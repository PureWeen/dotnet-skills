## Representation and trust boundary

`corpus/lock.json` is schema `resolver-corpus/1`: accepted parent, every logical path,
length and SHA-256, seed pins, recipe-store hashes, and canonical per-suite result-output hashes.
Those result hashes are rendered from committed **expected results**, never learned by running
a production classifier.

`expectations.json` owns the expected case/result documents separately from input construction.
`recipes.json` owns inputs and other retained documents. Both use a finite JSON DAG:
`s` is an interned string, `v` a scalar, `a` an ordered child array, `o` an ordered property list.
Child references must precede parents. Output `j`/`u` renders the original two-space JSON with
ASCII/non-ASCII spelling respectively; no semantic interpretation is performed.

Output `b` concatenates explicit `(offset,length)` slices from the shared `chunks.bin` byte
bank. This is **byte construction**, not a ZIP, PE, CMS, package-manager or scanner emulator.
The bank is deduplicated raw content-defined chunks, not a compressed archive hiding the
whole corpus. It deliberately preserves existing compressed streams, CRC errors, flags,
local/central disagreements, truncations, malformed PE/CMS structures and exact padding.
No writer round-trip or current compiler/zlib version can repair those witnesses.

Output `r` retains an exact named raw seed. The seed allowlist includes historical contracts,
the **single** SPDX catalog/policy provenance, genuine grant text, genuine assembly/module/CMS
controls, original control sources and the historical correlated checker. The public `.snk`
is a 276-byte CAPI PUBLICKEYBLOB (`06 02`, `RSA1`, 2048 bits), not a private key.
No genuine signed control was resigned or regenerated.

`corpus.py` validates store/seed hashes, finite resources, safe logical paths, exact output-set
equality, every output length/digest and canonical expected-output hashes before writing.
It refuses an existing output root. Fixed rejection/overwrite checks are in `test_corpus.py`;
these protect the representation, not extra row expectations.

## Replay without persistent generated files

From the repository root:

```text
python eng/blazor-package-resolver/tests/corpus.py verify --parent
python eng/blazor-package-resolver/tests/test_corpus.py
python eng/blazor-package-resolver/tests/lp04_expectations.py
python -O eng/blazor-package-resolver/tests/lp04_expectations.py
python eng/blazor-package-resolver/tests/corpus.py replay lp04
dotnet run --project eng/blazor-package-resolver/tests/ResolverChecks.csproj
dotnet run --configuration Release --project eng/blazor-package-resolver/tests/ResolverChecks.csproj
python eng/blazor-package-resolver/tests/test_shipping.py
```

The eleven legacy Python entrypoints are thin launchers. They materialize a new temporary root,
copy the historical sources from `oracles/` (LP-01 includes the reviewed declaration
correction; LP-02 includes the public-availability correction; all other oracles
are unchanged). LP-03 instead selects `lp03_sbom_expectations.py`, the independent
current-profile stdlib parser/package/LP-01-oracle specification; the original
`oracles/lp03_expectations.py` remains byte-identical historical evidence, not a
current positive test. They run the selected source there and
clean the temporary root on exit. Sibling paths, construction facts,
normal/optimized behavior and all arguments remain intact. The launchers never call production.

Native ResolverChecks independently classify the same byte-pinned materialized inputs.
They invoke Python **only to materialize bytes**, never to obtain a classification or expected
answer. Each run owns and disposes a fresh root; stale output-directory fixtures are ignored.
`corpus.py replay <foundation|lp01|...|lp10|pi01>` materializes, invokes the production CLI and
cleans up. No checked-in or pre-existing generated tree is needed by CI or local checks.
The installed-plugin smoke check additionally needs the full-report consumer's .NET 11 SDK.
It checks isolated, read-only installation, offline package/request execution, full-result
grader goldens and six fixed incorrect-result mutations, plus confirmed static-JSON handoff.
These are deterministic tests, not model evaluations.

For manual inspection only, `corpus.py materialize --output <new-isolated-directory>` exposes
the complete original logical tree. The operator owns cleanup of that explicit directory;
keep it outside the checkout. `compact_corpus.py` documents the one-shot representation
compiler: it accepts the untouched original fixture tree, never production results.

## PI-01 independence correction

**Do not interpret the historical PI-01 checker as an independent semantic/cryptographic
oracle.** Its 1,041-line managed validation block is correlated with production.
Historical source/contract bytes remain archived to preserve accepted construction and pins;
their old independence wording is superseded by this explicit narrower claim.

The independent boundary is exact public/genuine seed provenance, parent-byte equivalence,
synthetic construction recipes, and a small separate Python check of PE/CLR header construction
facts and the public-only key. That check does not validate the full metadata grammar, RSA,
CMS or publisher identity. Native production conformance/boundary checks and all 138 frozen
PI-01 scenarios still execute, but agreement with the historical correlated checker is
conformance evidence, **not an independent correctness proof**. No common validator was
deduplicated into production.

LP-04 D-lite `2.0.0` retires the v1 deciding oracle/counterfactual machinery. Its historical
oracle, seeds and optional `acceptance.json` remain archival only, not active expectations
or a verified/gap fallback. Only `lp04/cases.json` receives the named result-only D-lite
delta: missing root -> `missing-package`, duplicate/casefold-alias root -> `input-invalid`,
all other synthetic legacy packets -> `legacy-protocol`. Inputs, metadata, rationales,
recipes, chunks, seeds and the other ten rows stay byte-identical.
`corpus.py check_parent_file` reconstructs this independently specified delta and rejects
any extra mutation. The new `oracles/lp04_dlite_expectations.py` checks the construction
facts without importing production; the launcher runs it in ordinary and optimized Python.
Native D-lite checks cover package layouts, unsupported candidates, all five suffixes,
empty/large/512-asset inventories, pre-stream expansion/count bounds, strict ZIP/nuspec
safety, exact per-asset hashes and canonical inventory determinism. All six reasons are
not tested with follow-up, including empty supported layouts; no legal/origin/notice
conclusion or universal N/A is inferred. Retained real-package replay is separate from
the retired optional v1 acceptance manifests. npm/review/verified/gap/validator-v2 work is deferred.
The installed production build contains no LP-04 weakening entrypoint or label table.

The materializer authenticates no external review, inventory completeness, legal fact or
publisher. Proprietary retained archives are never seeds; only their existing optional
identities and full expectations are retained.
